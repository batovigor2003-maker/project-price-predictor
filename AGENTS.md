# AGENTS.md

## Проект

- Проект: прогноз изменения цен на авиабилеты для российского рынка и совет, купить сейчас или подождать. MVP ограничен авиабилетами; прогноз цен на туры возможен позже.
- Идея, главный сценарий и ограничения — `specs/01-продуктовая-идея.md`.
- Как запустить — `README.md`, когда в проекте появится приложение.

## Как со мной работать

- Отвечай по-русски, простыми словами: я не разработчик.
- Продуктовые решения принимаю я: чего нет в спецификации — спроси, не додумывай.
- Перед необратимым действием спроси: удаление данных, перезапись истории Git.
- Сделал — скажи, как проверить результат руками.

## Язык кода

- Код и всё, что к нему относится, — на английском: имена файлов, переменных, функций, таблиц и полей, комментарии, логи, коммиты, ветки, PR.
- На русском — только тексты интерфейса, которые видит пользователь, и `README.md`.

## Стек

- Фреймворк: Next.js (App Router).
- Язык: TypeScript.
- Интерфейс: React, Tailwind CSS, shadcn/ui.
- База данных: PostgreSQL в Docker.
- ORM: Drizzle; схема таблиц и миграции хранятся в коде.
- Доступ к данным: только с сервера, без прямого обращения браузера к базе данных.
- Пакетный менеджер: pnpm.
- Источник ценовых данных и способ построения прогноза пока не выбраны; согласуй их перед реализацией.

## Как вносим изменения

### Ветки и PR

- Любое изменение делай в отдельной рабочей ветке. Выбирай имя по сути изменения, без префиксов, например `keep-in-touch`. В `main` вноси изменения только через PR.
- По команде «Начинаем фичу / доработку / правку» или `/opsx:propose` переключись на `main`, забери изменения с GitHub, удали локальные ветки, которых больше нет на GitHub, и создай новую ветку от свежего `main`.
- Перед первой правкой файлов проверь текущую ветку. Если ты на `main` или текущая ветка уже влита, обнови `main` и создай от него новую ветку. Если текущая рабочая ветка ещё не влита, продолжай в ней.
- По команде «Коммить и пуш» создай коммит в текущей ветке, отправь её на GitHub, открой PR в `main` и пришли ссылку на него.
- После слияния PR переключись на `main`, забери изменения с GitHub и удали локальную ветку, которую влили.
- Изменения GitHub Actions и скриптов в `deploy/` вноси тем же путём, через PR.

### Правка и фича

- Для мелкой правки, в том числе небольшого изменения модели данных, составь план в режиме планирования, внеси правку в рабочей ветке и проведи её через PR.
- Для фичи пройди полный цикл от требований и плана до поэтапной реализации. Можно использовать любой инструмент, например OpenSpec.
- Фича готова, когда выполнены критерии приёмки из её спецификации.

### Данные

- Запускай миграции отдельным шагом до запуска приложения с новым образом. Разовый контейнер из того же образа применяет миграции и завершается. Если миграции завершились с ошибкой, останови выкатку до запуска приложения с новым образом.

## Выкатка в прод

### Окружения и сервер

- На сервере запускай приложение через Docker Compose с именем проекта `prod`. Во всех командах для продакшена используй `docker compose -p prod` и явно указывай файл конфигурации приложения.
- Сервер общий для приложения и лендинга. Добавляй только файлы, ключи и конфигурацию своего приложения. Существующие файлы, ключи и настройки Nginx других проектов оставляй без изменений. Удаление чужих ресурсов допускается только с моего явного согласия. Если меняешь конфигурацию Nginx приложения, выполни `nginx -t` перед её применением.
- Храни продакшен-секреты на сервере или в GitHub Actions Secrets. Исключи их из репозитория, образа и логов. Держи данные PostgreSQL в постоянном томе, доступ к базе оставляй внутри сервера.
- Задай ограничения по размеру и числу файлов логов контейнеров приложения. После успешной выкатки оставляй на сервере два последних успешно выкаченных образа приложения: текущий и предыдущий. Очищай только старые образы этого приложения, которые не используются контейнерами. Глобальная очистка Docker на общем сервере запрещена.

### Как выкатываем

1. Храни скрипты выкатки в `deploy/`. В GitHub Actions описывай запуск и вызовы скриптов. Перед серверной частью выкатки копируй на сервер скрипты из того же коммита, из которого собран образ.
2. После push в `main` запускай проверки проекта. Если они прошли, собери образ, присвой ему тег с полным SHA коммита и опубликуй в GitHub Container Registry (GHCR). На сервере используй этот тег на всех шагах релиза.
3. Выполняй серверные выкатки по одной. Скачай образ из GHCR и зафиксируй SHA текущей версии. Примени миграции из нового релиза, затем запусти приложение с новым образом. Миграции должны быть совместимы с версией приложения, которая работает до переключения. Перед миграцией, которая удаляет данные или нарушает совместимость, согласуй со мной порядок работ и восстановления.
4. Проверь, что запущен образ с нужным SHA и что публичный адрес `/health` по HTTPS возвращает `200`. Повторяй проверку только в пределах заданного времени запуска. После успеха очисти старые образы приложения по правилам выше.
5. Сообщи, какой SHA выкачен, дай ссылку на запуск GitHub Actions и результат проверки `/health`. Приложи публичную ссылку на приложение и короткие шаги для ручной проверки основного сценария.

### Сбой и откат

- Ошибка на любом обязательном шаге, включая миграции и проверку `/health`, означает, что выкатка завершилась с ошибкой. Останови следующие шаги выкатки и очистку образов. Сообщи мне, где произошёл сбой, что уже успело измениться, какой образ сейчас запущен и где посмотреть логи.
- Откат выполняй только по моей явной команде. Автоматический откат в workflow и скриптах запрещён. Перед ручным откатом проверь совместимость предыдущего образа с текущей схемой PostgreSQL. Если нужно менять схему или восстанавливать данные, отдельно согласуй это со мной. После согласованного отката снова проверь `/health` и сообщи, какая версия работает.
